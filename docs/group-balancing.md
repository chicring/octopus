# Group Balancing Guide

Author: 颖馨瑶 (Ying Xinyao)  
Contact: admin@loserrc.com | QQ: 1129414920  
Version: v0.1.2  
Date: 2026-05-27

本文说明分组里的轮询、随机、故障转移和加权分配模式应该在什么场景下使用，以及哪些字段会影响实际路由。

## 快速选择

| 分组类型 | 适合场景 | 主要配置 | 不适合场景 |
| --- | --- | --- | --- |
| 轮询 Round Robin | 多个渠道质量、成本、限额接近，希望请求均匀分摊 | 保持相同优先级，渠道启用即可 | 渠道质量差异很大，或需要主备 |
| 随机 Random | 需要打散突发流量，降低固定顺序带来的热点 | 保持渠道池健康，配合熔断 | 需要严格均匀或可预测顺序 |
| 故障转移 Failover | 主渠道优先，备用渠道只在失败后接管 | `priority` 数值越小越优先 | 希望所有渠道长期分摊成本 |
| 加权 Weighted | 渠道配额、性能、价格不一致，需要按比例分配 | `weight` 越大越优先参与 | 只需要主备，或权重无法长期维护 |

## 路由层级

一次请求的选择顺序是：

1. 先按请求模型找到启用分组。
2. 分组模式决定渠道尝试顺序。
3. 每个渠道内部再按 Key 状态选择可用 Key。
4. 如果 Key 配置了模型白名单，只会承接白名单里的模型。
5. Key 倍率参与渠道内选择评分：`score = total_cost * multiplier`，评分越低越优先。

## 模式说明

### 轮询 Round Robin

请求按渠道列表循环分配。适合多个同级渠道，例如同一家供应商的多个代理地址，或者多家供应商质量接近。

建议：
- 所有渠道保持相近模型能力。
- Key 倍率保持 `1`，除非某个 Key 成本明显更高。
- 如果模型支持不同，优先用 Key 模型白名单隔离。

### 随机 Random

每次请求随机打乱渠道顺序。适合突发流量明显、渠道没有强顺序要求的场景。

建议：
- 配合健康检查和熔断。
- 不要把明显不稳定的渠道放进同一个随机池。

### 故障转移 Failover

按 `priority` 从小到大尝试。主渠道失败、限流或无可用 Key 后，才进入备用渠道。

建议：
- 主渠道 `priority = 1`，备用渠道 `priority = 10/20`。
- 高价但稳定的渠道适合作备用。
- 不要把所有渠道都设同一个优先级，否则就失去主备意义。

### 加权 Weighted

按 `weight` 影响渠道排序，权重越高越容易被优先尝试。适合渠道配额或性能不同的场景。

建议：
- 大配额渠道给高权重，小配额渠道给低权重。
- 价格高的渠道降低权重或提高 Key 倍率。
- 定期复盘失败率和成本，权重不是一次性配置。

## Key 级模型隔离

如果同一个渠道有多个 Key，且每个 Key 支持的模型不同：

- 在 Key 的“支持模型”里写逗号分隔模型名，例如 `gpt-4.1,gpt-4.1-mini`。
- 留空表示继承渠道模型，所有模型都可以尝试。
- 请求 `gpt-4.1` 时，只会选择支持 `gpt-4.1` 或模型白名单为空的 Key。
- 测试单个 Key 时，如果模型不在白名单内，会返回明确的“不支持该模型”结果。

## 首字超时推荐

分组编辑里的首字超时支持推荐值。推荐逻辑基于当前分组已选模型最近 3 天成功请求的 `ftut` 首字时间：

1. 只统计成功请求，过滤错误日志和没有首字时间的记录。
2. 使用 P95 分位数代表“绝大多数正常慢请求”的边界。
3. 推荐秒数为 `ceil(P95 * 1.25 / 1000)`，保留 25% 缓冲。
4. 推荐值不会自动覆盖配置，需要手动点击套用。

如果暂无样本，说明最近日志不足，需要先运行一段真实流量，或暂时使用人工经验值。

## CLI Key 与普通 Key

CLI Key 是用于 Codex/CLI 类协议的凭证，不等同于普通 Bearer API Key。

- CLI Key 需要打开 “CLI 密钥” 标识。
- 普通模型列表刷新会跳过 CLI Key，避免把 CLI 凭证当普通 API Key 请求 `/models`。
- Codex OAuth 或 Auth 文件导入的 Key 会自动标记为 CLI Key。
- 非 CLI Provider 使用 CLI Key 测试会返回明确错误。

## RCA

### v0.1.2 - Channel Balancing and CLI Key Metadata

**Issue**: 同一渠道内多个 Key 支持模型不一致时，路由只按渠道模型匹配，可能把请求发给不支持目标模型的 Key；CLI 凭证在普通模型刷新里会被当作 Bearer API Key 使用，导致 401/404 或无法测试。

**Trigger**: 渠道配置多个 Key，其中部分 Key 为 Codex/CLI JSON 凭证，或部分 Key 只支持某几个模型；用户点击“刷新模型”或发起指定模型请求。

**Root Cause**: 原 Key 选择算法只有启用状态、429 冷却和累计成本维度，没有 Key 类型、Key 级模型白名单和倍率评分；模型列表刷新也没有区分 CLI 凭证与普通 API Key。

**Fix**: 新增 Key 的 `is_cli`、`multiplier`、`models` 元数据，路由和测试按请求模型过滤 Key；模型列表刷新只使用非 CLI Key；渠道编辑新增官网和用量查询预设配置，用于后续接入统一用量刷新链路。
